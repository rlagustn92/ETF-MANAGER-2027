## 버그 1. NaN / 무한대 비중이 들어오면 앱이 죽는다

**문제점**
전술 JSON 에 `"target_weight": 1e400` (무한대) 이나 NaN 이 들어 있으면 그대로
저장되고, 계산할 때 `calculate_integer_shares` 의 `math.floor()` 에서 터집니다.

```
services/calculation_service.py:57
  return math.floor(target_amount / price_per_share)
  ValueError: cannot convert float NaN to integer
  OverflowError: cannot convert float infinity to integer
```

**안 고치면 일어날 일**
- 그 전술 파일을 불러온 사람은 **화면 전체가 빨간 에러**가 됩니다.
- 포트폴리오가 세션에 남아 있어서 **새로고침해도 계속 죽습니다.**
- 복구는 `초기화` → `네, 바꿀게요` 2클릭으로 가능하지만, 빨간 에러 화면에서
  그걸 찾아 누를 사람은 많지 않습니다. 대부분 그냥 나갑니다.
- 지금 전술 JSON 공유를 권장하고 있으므로, **한 사람의 깨진 파일이 여러 명을
  죽입니다.**

**개선방안 1 — 모델에서 값을 받을 때 걸러낸다 (`Security.__post_init__`)**
비중이 숫자가 아니거나 NaN/무한대/음수면 `0.0` 으로 바꾸고 넘어갑니다.
- 장점: **한 곳만 고치면 모든 경로가 막힙니다** (JSON 불러오기, 코드 생성, 컴포넌트).
  앱이 절대 안 죽습니다.
- 단점: 값이 조용히 0 이 되어서, 사용자는 "내 비중이 왜 0 이지?" 하고 이유를 모릅니다.

**개선방안 2 — 불러오기에서 파일을 거부하고 이유를 알려준다 (`Portfolio.from_dict`)**
`3번째 종목의 비중이 숫자가 아닙니다` 처럼 이유를 붙여 `st.error` 로 안내.
- 장점: 사용자가 **뭐가 잘못됐는지 알 수 있고**, 기존 전술도 안 망가집니다.
- 단점: 이 경로(파일 불러오기)만 막습니다. 다른 경로로 NaN 이 들어오면 여전히 죽습니다.

> **추천: 1 + 2 둘 다.** 2 로 친절하게 안내하고, 1 을 최후의 안전망으로 둡니다.
> 계산 함수에 `if not math.isfinite(x): return 0` 한 줄을 더하면 3중 방어가 됩니다.

## 버그 2. 비중이 문자열이면 앱이 죽는다

**문제점**
`"target_weight": "많이"` 같은 값이 **검증 없이 그대로 저장**됩니다.
나중에 `f"{weight:.2f}"` 포맷팅에서 터집니다.

```
ValueError: Unknown format code 'f' for object of type 'str'
```

**안 고치면 일어날 일**
버그 1 과 같습니다. 전술 파일을 손으로 고친 사람(또는 다른 도구가 만든 파일)에서
발생하고, 화면이 통째로 죽습니다.

**개선방안 1 — `float()` 변환을 시도하고 실패하면 0 으로**
- 장점: 한 줄. `"0.3"` 같은 문자열 숫자도 알아서 처리됩니다.
- 단점: 버그 1 과 같은 "조용히 0" 문제.

**개선방안 2 — 타입을 검사해 파일을 거부**
- 장점: 원인이 분명히 전달됩니다.
- 단점: 옛날에 만든 정상 파일에 문자열 숫자(`"0.3"`)가 있으면 갑자기 못 열게 됩니다.

> **추천: 1.** 버그 1 과 같은 함수에서 같이 처리하면 코드가 한 군데로 모입니다.

## 버그 3. 환율이 0 이나 음수로 들어오면 앱이 죽는다

**문제점**
환율 **조회 실패**(데이터 없음)는 잘 처리됩니다 — 경고를 띄우고 화면은 삽니다.
그런데 조회는 성공했는데 **값이 0 이나 음수**면 `to_krw()` 가 예외를 던지고
아무도 안 받습니다.

```
services/calculation_service.py:192
  if usdkrw is None or usdkrw <= 0: raise ValueError(...)
```

**안 고치면 일어날 일**
- 데이터 소스가 잠깐 이상한 값을 주면 **미국 종목을 담은 모든 사용자의 화면이 죽습니다.**
- 조회 실패보다 오히려 더 나쁩니다. 실패는 대비돼 있는데 "이상한 값"은 무방비입니다.
- 캐시에 0 이 한 번 저장되면 캐시가 만료될 때까지(1시간) 계속 죽습니다.

**개선방안 1 — `fx_service` 에서 값을 검증한다**
`rate <= 0` 이거나 유한하지 않으면 `ok=False` 로 바꿔 "조회 실패"와 같은 길로 보냅니다.
- 장점: **이미 잘 동작하는 실패 경로를 재사용**합니다. 새 UI 가 필요 없습니다.
  환율을 쓰는 모든 곳이 한 번에 보호됩니다.
- 단점: 없다시피 합니다. 굳이 꼽자면 "0원 환율"이라는 정상 상황은 존재하지 않으므로 안전.

**개선방안 2 — `to_krw` 가 예외 대신 `None` 을 돌려준다**
- 장점: 호출하는 쪽이 각자 판단할 수 있습니다.
- 단점: **호출부를 전부 고쳐야** 하고, 하나라도 빠뜨리면 `None` 이 흘러다니다 다른 데서 터집니다.

> **추천: 1.** 명백히 이게 낫습니다. 고치는 데 세 줄이면 됩니다.

# 🟠 중대 — 안 죽지만 틀린 숫자가 나갑니다

## 버그 4. 갓 상장한 ETF 의 분배율이 터무니없이 부풀려진다

**문제점**
상장 12개월 미만 종목은 "실제 관측 기간 → 365일" 로 연환산합니다.
그런데 **관측 기간에 하한이 없습니다.**

| 실제 지급 | 관측 기간 | 화면에 뜨는 분배율 |
|---|---|---|
| 2회 | 3일 | **243%** |
| 2회 | 15일 | **52%** |
| 12회 | 12개월 | 12% (정상) |

```
services/distribution_service.py:141
  annualized = total * (DAYS_PER_YEAR / actual_days)   # actual_days=3 이면 121배
```

**안 고치면 일어날 일**
- 주간분배(위클리) ETF 는 상장 2주면 2회를 지급합니다. **현실에서 자주 일어납니다.**
- 화면에 `분배율 243%`, `월 분배금 2,400만원` 같은 숫자가 뜹니다.
- 그 숫자가 **캡처 이미지에 박혀서 커뮤니티로 퍼집니다.** 지금 하시는 공유 용도에서
  제일 위험합니다.
- "추정치" 경고가 붙긴 하지만, 경고는 작고 숫자는 큽니다.

**개선방안 1 — 최소 관측 기간을 둔다 (예: 90일)**
90일이 안 되면 연환산하지 않고 "아직 분배율을 계산할 수 없습니다"로 안내.
- 장점: 간단하고, 말이 안 되는 숫자가 원천 차단됩니다.
- 단점: 상장 1~2개월 된 인기 ETF 의 분배율이 **아예 안 나옵니다.**
  지금 예시에 들어있는 종목도 일부 해당돼서 체감이 큽니다.

**개선방안 2 — 연환산 배수에 상한을 둔다 (예: 최대 6배)**
- 장점: 숫자가 계속 나오되 폭주는 막힙니다. 기존 동작이 크게 안 변합니다.
- 단점: 상한에 걸린 값은 **여전히 부정확**합니다. "왜 6배인가"의 근거가 약합니다.

**개선방안 3 — 분배율만 숨기고 실제 지급액은 그대로 보여준다**
`분배율 243%` 대신 `최근 3일간 2회 지급, 주당 200원 (연환산 불가)`.
- 장점: **거짓말을 안 합니다.** 사용자는 사실만 보고 직접 판단합니다.
- 단점: 포트폴리오 합계(월/연 분배금)에서 이 종목을 빼야 하는데, 그러면 합계가
  실제보다 작아 보입니다. 처리할 게 늘어납니다.

> **추천: 1 (90일) + 3 의 안내문구.** 90일 미만이면 "실제 지급 N회 / 주당 X원"만
> 보여주고 연환산은 하지 않습니다. 지금 캡처 이미지가 퍼지고 있어서, 부정확한
> 숫자보다 "아직 모른다"가 낫습니다.

## 버그 5. 백테스트 결과가 낡은 채로 남는다

**문제점**
백테스트를 돌린 뒤 **종목을 지우거나 시드를 바꿔도 예전 결과가 그대로 화면에
남아 있습니다.** 결과가 어느 시점 포트폴리오의 것인지 표시가 없습니다.

실측:
- 2종목으로 백테스트 → 1종목 삭제 → **화면 결과는 여전히 2종목**
- 시드를 1,000만 → 5,000만 변경 → **백테스트 "초기 투자금"은 계속 1,000만**

**안 고치면 일어날 일**
- 사용자가 종목을 바꿔가며 비교할 때 **바뀐 줄 알고 옛날 결과를 읽습니다.**
- 캡처해서 공유하면 **현재 포폴과 다른 백테스트 수치**가 같이 퍼집니다.
- 매우 흔한 동선입니다. 백테스트는 원래 이것저것 바꿔보는 기능이니까요.

**개선방안 1 — 포트폴리오가 바뀌면 결과를 지운다**
종목 구성·시드의 지문(해시)을 결과와 함께 저장하고, 달라지면 `bt_result` 를 비웁니다.
- 장점: 틀린 걸 아예 못 보게 됩니다. 가장 확실합니다.
- 단점: 살짝만 건드려도 결과가 사라져서 **"방금 본 게 어디 갔지"** 가 될 수 있습니다.

**개선방안 2 — 지우지 않고 "낡았다"고 표시한다**
`⚠ 이 결과는 종목을 바꾸기 전 것입니다. 다시 실행하세요` + 결과를 흐리게.
- 장점: 비교용으로 남겨둘 수 있고, 오해도 막힙니다.
- 단점: 사용자가 경고를 무시하고 캡처할 수 있습니다.

**개선방안 3 — 결과 위에 "무엇을 돌린 것인지" 항상 적는다**
`2026-09-15 기준 · 9종목 · 시드 1억 으로 실행한 결과`
- 장점: 낡든 아니든 **맥락이 항상 붙습니다.** 캡처에도 같이 나갑니다.
- 단점: 그것만으로는 사용자가 차이를 못 알아챌 수 있습니다.

> **추천: 2 + 3.** 지우지 말고, 낡았으면 경고를 띄우고, 결과에는 항상 "무엇을
> 돌렸는지"를 적습니다. 3 은 공유 이미지에도 도움이 됩니다.

## 버그 6. 매수 입력에 NaN 이 들어오면 비중이 100% 가 된다

**문제점**
금액/수량 입력 컴포넌트가 NaN 을 보내면 비중이 조용히 **1.0(=100%)** 이 됩니다.
천문학적 금액(1e30)도 마찬가지로 100% 로 잘립니다.

**안 고치면 일어날 일**
- 브라우저 쪽에서 계산이 틀어지면(입력 중간 상태 등) **비중이 갑자기 100% 로 튑니다.**
- 사용자가 모르고 지나가면 다른 종목 비중이 전부 눌립니다.
- 재현이 어려워서 "가끔 비중이 이상해진다"는 제보로만 올 유형입니다.

**개선방안 1 — 컴포넌트에서 온 값을 받을 때 유한성 검사**
숫자가 아니거나 NaN/무한대면 **무시**하고 기존 비중을 유지합니다.
- 장점: 사용자가 아무것도 잃지 않습니다.
- 단점: 값이 조용히 무시돼서, 진짜 입력이 씹히면 이유를 모릅니다(가능성은 낮음).

**개선방안 2 — 브라우저(JS)에서 보내기 전에 막는다**
- 장점: 애초에 이상한 값이 서버로 안 옵니다.
- 단점: **JS 만 고치면 파이썬은 여전히 무방비**입니다. 컴포넌트 값은 결국
  외부 입력이라 서버에서도 검사해야 합니다.

> **추천: 1 (필요하면 2 도 같이).** 외부에서 들어오는 값은 받는 쪽에서 검사하는 게 원칙입니다.

## 버그 7. "정말 바꿀래요?" 확인창이 안 사라진다

**문제점**
예시 버튼을 눌러 확인창이 뜬 상태에서 **다른 동작을 해도 계속 떠 있습니다.**
`취소` 를 눌러야만 없어집니다.

**안 고치면 일어날 일**
사용자가 마음을 바꿔 다른 걸 하면, 화면 위쪽에 경고가 계속 남아 방해합니다.
실수로 `네, 바꿀게요` 를 누르면 **작업하던 포트폴리오가 날아갑니다.**

**개선방안 1 — 다른 동작이 일어나면 자동으로 확인창을 닫는다**
- 장점: 자연스럽습니다.
- 단점: "다른 동작"의 범위를 정해야 합니다(종목 선택? 비중 변경? 전부?).

**개선방안 2 — 확인을 `st.dialog` 모달로 바꾼다**
- 장점: 모달은 닫기 전까지 다른 조작이 안 되므로 애매함이 사라집니다.
- 단점: Streamlit 버전 의존성이 생기고, 모바일에서 답답할 수 있습니다.

> **추천: 1.** 종목 추가/삭제/선택이 일어나면 `preset_pending` 을 비우면 됩니다.

## 버그 8. 종목 한도를 26 → 11 로 줄이면 초과 상태가 그대로 남는다

**문제점**
26개를 담고 `종목 더 담기` 토글을 끄면 **보유는 26개인데 한도는 11** 이 됩니다.
안내가 전혀 없고, 이후 종목을 추가하려 하면 그때서야 거부됩니다.

**안 고치면 일어날 일**
"왜 더 못 담지?" 하고 혼란스러워합니다. 죽지는 않습니다.

**개선방안 1 — 보유 개수가 한도를 넘으면 토글을 못 끄게 한다**
- 장점: 모순 상태가 아예 안 생깁니다.
- 단점: 왜 안 꺼지는지 설명이 필요합니다.

**개선방안 2 — 끌 수는 있게 하되 안내문을 띄운다**
`지금 26개를 담고 있어 한도(11개)를 넘습니다. 더 담으려면 다시 켜세요.`
- 장점: 자유를 뺏지 않습니다.
- 단점: 모순 상태는 남습니다.

> **추천: 2.** 사용자가 하려는 걸 막기보다 알려주는 쪽이 낫습니다.

## 버그 9. 이름표는 20자까지 쓸 수 있는데 8자만 보인다

**문제점**
`전술판 이름표` 입력칸은 `max_chars=20` 인데, 카드에 들어가는 폭은 한글 8.6자입니다.
20자를 쓰면 **화면에서 그냥 잘립니다.**

**안 고치면 일어날 일**
사용자가 길게 쓰고 나서 잘린 걸 보고 실망합니다. 데이터가 상하지는 않습니다.

**개선방안 1 — 입력 한도를 10자 정도로 줄인다**
- 장점: 못 쓰게 하면 실망할 일이 없습니다.
- 단점: 영문 이름은 10자가 짧습니다(`COVERED CALL` 이 12자).

**개선방안 2 — 입력하는 동안 미리보기를 보여준다**
`카드에는 이렇게 보입니다: 가나다라마바사아` + 넘치면 빨갛게.
- 장점: 사용자가 스스로 조절합니다. 한도를 줄일 필요도 없습니다.
- 단점: 화면에 요소가 하나 늘어납니다.

> **추천: 2.** 지금 이름표 옆에 작은 회색 글씨 한 줄이면 됩니다.

## 버그 10. 전술 파일로는 같은 종목을 두 번 담을 수 있다

**문제점**
UI 로는 잘 막힙니다(`이미 추가된 종목입니다`). 그런데 **JSON 으로는 통과**합니다.
`Portfolio.from_dict` 가 `add()` 를 안 거치기 때문입니다.

**안 고치면 일어날 일**
전술판에 같은 종목이 두 장 뜨고, 비중 합계가 이상해집니다. 죽지는 않습니다.

**개선방안 1 — 불러올 때 중복을 합친다**
비중을 더해서 하나로.
- 장점: 사용자가 뭘 안 잃습니다.
- 단점: "왜 비중이 합쳐졌지" 할 수 있어 안내가 필요합니다.

**개선방안 2 — 뒤에 나온 중복을 버리고 경고**
- 장점: 단순합니다.
- 단점: 비중이 사라집니다.

> **추천: 1 + 안내문구.**

## 버그 11. 전술 파일의 종목 수 제한이 없다

**문제점**
`positions` 에 500개를 넣으면 그대로 들어옵니다. 슬롯은 26개뿐이라
**474개가 슬롯 없이 전술판 한가운데 겹쳐서** 그려집니다. (죽지는 않음)

**안 고치면 일어날 일**
장난 파일이나 다른 도구가 만든 파일에서 화면이 엉망이 됩니다. 느려집니다.

**개선방안 1 — 슬롯 수(26)를 넘으면 거부**
- 장점: 명확합니다.
- 단점: 26개를 살짝 넘는 파일을 통째로 못 열게 됩니다.

**개선방안 2 — 앞에서 26개만 담고 나머지는 버리며 안내**
`종목이 500개라 비중이 큰 26개만 불러왔습니다.`
- 장점: 일단 열립니다.
- 단점: 조용히 버려지는 게 있어 오해 소지.

> **추천: 2.**

# 문제 없던 것들 (확인함)

- 검색어 10종(빈 값, 500자, SQL 주입 모양, 이모지, 역슬래시) — 전부 안전
- 시드 입력칸 9종(빈 값, 문자, 음수, 콤마 범벅, 20자리 숫자) — 전부 안전
- 환율 **조회 실패** — 경고를 띄우고 화면은 정상 (제대로 만들어져 있음)
- 백테스트 경계 — 미래 날짜/오늘/주말/종목 0개/투자금 0원 모두 정상 처리
- UI 에서 같은 종목 또 담기 — 잘 막힘
- 26종목 전술판 렌더링 — 겹침 없음
- 가격 0원, 시드 0원 — 화면 정상
